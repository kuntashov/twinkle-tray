## D1 — Base and compatibility

**Question:** Patch installed 1.17.2 or current upstream? **Evidence:** installed commit `0ffa0ac5aa5af31affee69dd18796d6897646a07` and pinned upstream `f4b36e12e2dbedd415a588b9baa2b8c65cf01f30` share scheduler risks; upstream already has worker-ready waits, generation-aware inventory queues, resume coalescing and startup grace. **Options:** backport those mechanisms to 1.17.2; build the local correction on pinned upstream. **Chosen:** pinned upstream, reuse its infrastructure. **Consequence:** deliverable is a tested fork build based on 1.18.0-beta2, not an assertion of drop-in 1.17.2 compatibility. **Reversal trigger:** a demonstrated regression specific to the upstream base requiring a smaller backport.

## D2 — Manual brightness ownership

**Question:** Should same-event recovery force the schedule value? **Evidence:** current forced lifecycle calls erase manual corrections; a new readiness delay also creates a window before first schedule acceptance. **Options:** force on every unlock; protect only successfully applied intervals; protect manual intent for the current per-display interval even while schedule is pending. **Chosen:** non-animated manual override survives tick/same-event recovery, including manual before first acceptance. New full-date/event/settings identity or explicit UseTime expires it. Overrides are in-memory for the process lifetime; external/cold restart returns to existing startup/checkTimeAtStartup policy, without new persistence. LERP retains regular ticks and invalidates pending old work only. **Consequence:** manual marker is distinct from schedule acceptance; peers can remain pending. Same-event recovery may restore the current manual/pre-idle value through the same owner. External restart scripts/tasks remain outside scope. **Reversal trigger:** explicit product request for a different override duration, persistence or animated hold.

## D3 — Readiness, pending and acceptance

**Question:** What must become ready and what counts as applied? **Evidence:** fulfilled refresh can return cached data; current inventory can be partial; native writes have no end-to-end physical acknowledgement. **Options:** fixed delay; wait for every historical known display; current eligible inventory with per-display acceptance. **Chosen:** worker plus usable current inventory, per-display pending/accepted state, never wait for disconnected historical IDs. Bound recovery readiness waiting to 30 seconds after existing wake delay; event-driven wakes and cleanup on timeout/exit/supersession, no permanent polling. This bound does not expire an already started smooth transition: it retains existing speed and cancellation policy, including valid durations over 30 seconds. Equivalent tick/recovery requests for the same valid intent do not restart it. **Consequence:** accepted means current software transport submission, not physical DDC success; later normal events/ticks can retry readiness. **Reversal trigger:** evidence a device requires a different bounded recovery window, handled as a separately justified policy change.

## D4 — Current targets and cancellation

**Question:** How to prevent old asynchronous work and known restore from winning? **Evidence:** cache precedes async refresh/read; existing inventory generation does not represent brightness intent; transport, throttle, feature-dependent and linked queues and smooth callbacks can all defer work. **Options:** extra force timeout; native acknowledgement redesign; one recovery owner with intent validity through existing paths. **Chosen:** one owner chooses schedule or permitted restore, recalculates current time/guards after waits and checks intent generation before deferred software sends. Immediately before actual IPC, after `sendNow`/queue waiting, it also re-evaluates interval/full-date/settings identity even without a token change or intervening trigger; stale interval work is dropped and current reconciliation requested. Manual invalidation follows actual brightness paths, not generic recent-interaction flags; unrelated volume/VCP remains unaffected. **Consequence:** already issued native calls cannot be recalled; software guarantee covers still-pending work. **Reversal trigger:** a reproducible native ordering issue that cannot be handled at the existing sender boundary.
